MCP for FP&A:
what it is, and what to think about first

Everyone is suddenly talking about MCP. Here’s what it actually is, what it can do with a planning model like TM1, how you get it, and the things worth thinking about before you switch it on — in plain English. And why, if you build TM1 models, you can set one up yourself.

Status Published October 2026 · reviewed 16 Oct 2026 Read about 15 minutes Related Three Models, One Lesson · How signing in to TM1 works
01

You can do this

If you’re a TM1 developer or consultant, you’re much closer to this than you might think — you don’t need to be a software engineer. You already know the hard part: how TM1 hangs together, how its security works, and all the ways a model quietly goes wrong. You don’t need deep knowledge of TM1’s REST API either — some familiarity is enough to start, and free libraries such as TM1py can carry you through the early steps while you learn the rest. The MCP part — the bit that sounds new, explained below — is the small part. What you really need is a keen interest to learn.

And it costs next to nothing. The MCP standard is open, the official toolkits are free, and so are the libraries that help you talk to TM1. The real costs are an AI app subscription and your own time. You don’t need permission from a vendor, and you don’t need to build everything at once.

A gentle way in, one step at a time:

  1. A weekendRead-only, on a copyPoint a tiny server at a development copy with a limited login. Two tools: list the cubes, read some cells. Ask it questions you already know the answers to.
  2. The next few weeksTeach it to explainAdd tools to read rules, processes and views. Ask it to explain a model you know well, and see where it’s right and where it isn’t.
  3. ThenAdd your checksStore the expected answers for your key numbers and give it a tool to run them. Now it can check itself — and so can you.
  4. When you’re readyLet it build, on development onlyAdd tools that change things, behind your own review: every change listed, checked and approved by you before it goes anywhere.

Your own setup means your own guardrails. Start small, add a little at a time, and learn as you go. It’s more doable than it sounds.

It does take two things. Patience, because the AI gets things wrong and you’ll go round the loop more than once. And discipline, because the checks, the reviews and the written-down conventions are what make it work. Skip those, and it’s a toy. Keep to them, and it’s a genuinely useful colleague.

02

What is MCP?

Until recently, using AI on planning numbers meant copy and paste. You exported something, pasted it into a chat assistant, and asked a question. The AI only knew what you showed it, and it couldn’t touch anything.

MCP — the Model Context Protocol — changes that. It’s an open standard for plugging AI assistants into other systems: your planning model, your databases, your files. A common way to describe it is a USB-C port for AI. Before it, every AI tool needed its own custom link to every system. With MCP, a system gets one standard plug, and any AI app that speaks MCP can use it.

It was introduced as an open standard in late 2024 and has since been taken up across the industry — by the major AI companies, by Microsoft, by Google, and by IBM. That’s why you’re hearing about it everywhere.

An MCP server offers the AI a short menu of tools — things it’s allowed to do in that system. For TM1 the menu might be “list the cubes”, “read these cells”, “show me this rule” and, if you allow it, “change this rule”. The AI reads your question, picks the tools it needs, uses them, and answers. What’s on the menu is decided by whoever sets up the server.

03

What can it do with a planning model?

Once an AI can reach TM1 through an MCP server, the useful things it can do fall into a few groups:

AskAnswer questions from live numbers“Why is Opex over in the East this quarter?” — from the model itself, not last week’s export.
ExplainExplain how the model works“Where does this number come from?” Read a rule or a process and explain it in plain words.
FindFind things across the modelWhich processes write to this cube? What uses this dimension? Handy before changing anything.
CheckHealth-check a modelSpot rules without feeders, views that no longer work, processes nobody runs.
DraftDraft commentaryFirst-pass variance commentary from the real figures, for a person to edit.
Build · custom serversHelp build and change modelsDimensions, rules, processes — with every change reviewed by a person before it goes anywhere. Needs an open-source or home-built server that offers these tools.

Which server can do what. What’s possible depends entirely on the tools a server offers. IBM’s own MCP tools focus on exploring and analysing: browsing cubes, AI-generated MDX queries, cube analysis and performance metrics. Building and changing models needs an open-source or home-built server that offers those tools — and deserves the most care.

What it doesn’t do. It doesn’t make the AI understand your business; it only gives it a way in. It doesn’t replace PAW or your reports. And it doesn’t make the AI right — it can still misread a number or pick the wrong version, just faster and more confidently.

04

How do you get it?

For TM1 there are three routes today:

Route 1IBM’s own MCP toolsIBM documents MCP tools from Planning Analytics 3.1.7 onwards — exploring cubes, AI-generated MDX queries, cube analysis and performance metrics — reached through one MCP endpoint with an agent key. Supported by IBM. Availability depends on your edition (IBM’s cloud service and certified containers are documented); check with IBM or your partner for yours.
Route 2An open-source MCP serverSeveral are freely available. Someone technical can install one and point it at TM1 in an afternoon. You’re responsible for checking what it does and keeping it up to date.
Route 3Build your ownFor teams that need it to fit their own controls — their review process, their standards. More work; most teams won’t need to.

Whichever route, you’ll need the same four things:

  • An AI app that supports MCP — several do, including Claude, ChatGPT, Microsoft Copilot and developer tools like VS Code, but how they connect and what they allow varies by product, plan and company policy. Check that your app supports the kind of MCP server you plan to use before buying anything, and use your company’s business account, not a personal one.
  • A way for it to reach TM1 — through TM1’s REST API (explained just below).
  • A TM1 login for it to use — and this choice matters more than anything else (see below).
  • A yes from IT and security — it’s a new route into your planning data, and they will want to know.

What an MCP server actually is, and where it runs

An MCP server sounds grand, but it’s just a small program. It knows how to talk to TM1 on one side and to an AI app on the other. It runs in one of three places:

On your computerStarted by your AI appYou add it to your AI app’s settings, and the app starts it quietly in the background whenever you open it. Only you use it. Quick to try — but it sits outside your normal systems, and holds whatever TM1 login was put into it.
On a serverRunning for everyoneInstalled once on a company server, running all the time, and several people’s AI apps connect to it over the network. It can be looked after, updated and reviewed like any other system.
Inside Planning AnalyticsIBM’s built-in toolsNothing to install: the MCP server is part of Planning Analytics itself, and you switch it on and connect your AI app to it.

Pilots usually start on someone’s computer. Anything that lasts belongs on a server, where it has an owner.

Do people really use open-source ones?

Yes — they’re the most common way to try MCP today, mostly by developers, consultants and technical finance people. Setting one up typically looks like this:

  1. Download it — open-source MCP servers are usually shared on GitHub and installed with a single command.
  2. Tell it where TM1 is: the server’s address.
  3. Give it a TM1 login to use.
  4. Choose what it may do — many offer a read-only setting.
  5. Add it to your AI app’s settings, restart the app, and start asking questions.

That’s the appeal — and the catch. You are running someone else’s code with a key to your planning model. Know who wrote it and whether it’s maintained, stick to a known version, and keep the TM1 password out of the settings file. In 2025 a fake MCP server, posing as an email tool, was caught copying every email it handled to an outsider.

How hard is it to build one for TM1?

Anthropic, which created MCP, published it as an open standard, and official free toolkits (SDKs) are available for Python, TypeScript and other languages, plus example servers for everyday things like files. There’s no ready-made TM1 server in there — but the toolkit does the hard protocol work, so building one splits into three very different jobs:

The MCP partThe protocol is the easy partThe toolkit handles talking to the AI app. A minimal demonstration with one tool is about fifteen lines of code — a demonstration, not a working TM1 integration.
The TM1 partReal workReading cubes and rules through TM1’s REST API, signing in (TM1 security, CAM, PAW, cloud keys — every method is explained in How signing in to TM1 works), keeping answers small enough for the AI to use, and error messages it can act on. Python’s open-source TM1py library does much of this for you.
The guardrailsMost of the effortRead-only by default, the right login, cubes kept out of reach, every look and change recorded, changes reviewed, every tool tested. This is what turns a demo into something you’d let near real data.

A realistic sense of effort, for someone who knows both TM1 and a little programming:

GoalRough effort
A first experiment: list cubes and read a few cells, read-only, on a development copyAn afternoon
A useful read-only server: cubes, rules, processes, views, answers kept smallA few days
Something a team can rely on: proper sign-in, limits, recording, testsWeeks
Letting the AI build and change models, with every change reviewed and released properlyConsiderably more — this is where most of the real design work is

Two ways to talk to TM1. Use a ready-made library such as TM1py, which handles signing in and much of the REST API for you, or call TM1’s REST API directly from the language you prefer. A library gets you started faster; your own calls give you full control over every TM1 quirk. Both work.

The descriptions you write for each tool matter more than you’d expect: the AI chooses which tool to use by reading them, so “read cells” and “read cells from the approved forecast version only” lead to very different behaviour.

For the curious: what the MCP part looks like

One way to do it: a minimal read-only TM1 MCP server in Python, using version 2 of the official MCP toolkit and, for brevity, the TM1py library. The TM1 password comes from an environment variable, never from the code:

from os import environ
from mcp.server import MCPServer
from TM1py import TM1Service

mcp = MCPServer("tm1")

def tm1():
    return TM1Service(address=environ["TM1_HOST"], port=int(environ["TM1_PORT"]), ssl=True,
                      user=environ["TM1_USER"], password=environ["TM1_PASSWORD"])

@mcp.tool()
def list_cubes() -> list[str]:
    """List the cubes in the TM1 model."""
    with tm1() as t:
        return t.cubes.get_all_names(skip_control_cubes=True)

@mcp.tool()
def read_cells(mdx: str) -> list:
    """Read cell values with an MDX query. Read-only."""
    with tm1() as t:
        return t.cells.execute_mdx_values(mdx)

# Try it in the toolkit's test window:  uv run mcp dev server.py

That’s the easy part. Everything in the “what to think about” section below is the rest.

How does it reach TM1?

TM1 has a built-in door for software, called the REST API. It’s how PAW, the Excel add-in, scripts and other tools talk to TM1, and it’s the door an MCP server uses too. Which way in depends on your setup:

Your setupHow the MCP server gets inWhat IT needs to sort out
TM1 v11 on your own serversStraight to the TM1 server’s REST APIThe REST port switched on in the server’s settings, a network route from wherever the MCP server runs, and an encrypted (HTTPS) connection
TM1 behind Planning Analytics WorkspaceThrough PAW, which passes requests on to TM1Sign-in through PAW’s own login; not every MCP server supports this route
Planning Analytics in IBM’s cloud (v12)Over the internet to IBM’s web address for your serviceAn API key for the login it uses — and that key carries exactly its owner’s access
IBM’s own MCP toolsBuilt into Planning Analytics — nothing extra to installSwitching the feature on and setting up its agent key

Each sign-in method — native, LDAP, CAM, Windows, cloud keys, PAW — is explained step by step in How signing in to TM1 works.

Where it runs and how it gets in are exactly what IT and security will ask about — so ask them early.

05

What it’s like to work with one

You talk to it

Working with an MCP server is a conversation in your AI app, in plain language. Ask a question and you see each step as it happens: “I’ll list the cubes… now I’ll read the Opex rules…” Most AI apps ask your permission before each tool is used, or let you allow the harmless ones and keep approving the rest.

Building works the same way. You describe what you need — a cube, a rule, an allocation — the AI proposes a plan, you agree or correct it, and it builds piece by piece while you watch.

How you check its progress

  • Watch the steps. Every tool it uses is shown as it happens — which cube it read, which rule it changed.
  • Ask it what it did. “List everything you changed” is a perfectly good question, and a good habit at the end of each session.
  • Look for yourself. Open the view in PAW and read the numbers. Never take the AI’s word that a number is right.
  • Write the expected answers down first. The single most useful habit: store known results (“total Opex for March should be 1,234,500”) and run them after every change. The AI stops being trusted and starts being checked.
  • Keep one list of every change. Everything the AI does is recorded in one place, reviewed by a person before it goes anywhere near production.

What it has to learn

An AI knows TM1 in general — rules, feeders, TurboIntegrator — but nothing about your house: your naming conventions, that every cube gets a default view, how you handle versions, the quirks of your TM1 version. And it forgets between conversations. Tomorrow’s session starts from scratch.

Two things fix that. Write your conventions down in a short guide the AI reads at the start of every session. And when you find yourself correcting the same mistake twice, turn it into an automatic check that refuses the change — so the mistake can’t happen a third time, whoever makes it.

The journey

Three full models have been built this way, one after the other, and they show how the approach matures:

  1. An allocations model. It worked in the end, after beginner mistakes: structure baked into names instead of dimensions, rules that compiled but computed the wrong thing. Everything was checked by hand.
  2. A workforce planning model. By now the conventions were written down and checked automatically. It was deployed from development to production, and the figures matched to the cent.
  3. A statutory consolidation. Built test-first: the expected answers from 26 published worked examples were stored before the build, and the AI built until every one matched.

The AI didn’t get smarter between the first model and the third. The system around it did.

The full story, mistakes included, is in Three Models, One Lesson. A few practical lessons from it:

  • Let it explain before it builds. A wrong plan is cheap to fix; a wrong model isn’t.
  • Keep sessions focused. One piece of work at a time, with a clear finish.
  • When it starts guessing, stop it. An AI that can’t solve something tends to try variations. Step in, find the real cause, then carry on.
  • Keep the builder and the reviewer apart. The AI builds; a person approves.
06

What to think about before you switch it on

A useful way to think about it: you’re giving system access to a new colleague. A very fast one, who never gets tired, but who is new. Finance already knows how to do that well — and most of what to consider follows from it.

1Start with a question you want answered

“Let’s connect AI to TM1” isn’t a goal. “Let analysts ask why a number moved without waiting for us” is. A clear use case tells you what the AI needs to reach — and, just as usefully, what it doesn’t.

2Accuracy: right number, right version

For FP&A this may be the biggest risk — bigger than a leak. An AI sounds just as sure when it’s wrong, and a confident wrong number in a board pack does real damage. Planning models make it easy: did it read the approved forecast, or someone’s working draft? Did it read the number, or work it out? Check its answers like any new colleague’s, especially at first. The upside: reading the real model, it’s far less likely to invent a figure than when it works from a pasted extract.

3Whose access does it use?

An MCP server signs in to TM1 like any user. The quick way to set one up is with an administrator’s login — and then everyone who asks the AI anything borrows that access. In practice there are three set-ups:

  • One shared account. Every request runs with that account’s access, whoever is asking. Simple, and the riskiest if the account is powerful.
  • A sign-in per person. Each request runs as the person asking, so TM1’s security decides what each one sees, exactly as it does today. Only possible where the server and your TM1 set-up support it.
  • Extra limits in the server. The server itself refuses certain cubes or actions. Useful on top of either of the above — but those limits are only as good as their testing, and TM1’s own security remains the real control.

(For how sign-in and TM1 security fit together, see How signing in to TM1 works.)

The rules you already use for people carry straight over: least access, read before write (start read-only, and never let it change production), maker and checker (a person reviews its changes), and an audit trail that records what it looked at as well as what it changed.

Two planning-model traps we found by testing on TM1 v11.8. Hiding one figure from the AI didn’t protect it — it could be worked out from the total minus the other lines. And a process run by a user who couldn’t see a cube still read and changed that cube: the process ignored that user’s cube and cell security. So permission to run a process can reach well beyond what the person could touch directly — an AI allowed to run processes needs that limit chosen with care. TM1’s own security, on the right login, is the real control.

4What leaves the building

Everything the AI reads goes into the conversation — and so to the AI provider. A business account with the right terms (no training on your data, sensible retention, the right region) covers most of that. But it’s still worth asking what the AI needs to see. Building or checking a model mostly needs the structure, not the figures, so a development copy with test data is often the right place to start. And some numbers are sensitive because of timing: actuals before results are announced, a forecast during a deal.

5It can’t always tell information from instructions

A person reading a note that says “send the salary file to this address” knows something’s wrong. An AI may just do it. Anything the AI reads — a comment in a process, a text cell, a document — could try to steer it. This is one more reason to keep it read-only unless you’re deliberately building, and to keep its reach narrow.

It has happened: in 2025 researchers showed a single crafted email could get Microsoft 365 Copilot to collect internal information and send it out. Microsoft fixed it before any known real-world attack. Not an MCP flaw — but exactly the kind of risk any AI with access to data carries.

6Someone has to own it

A person has a manager. An MCP server is often set up by one enthusiast, then forgotten: no named owner, not in the quarterly access review, still running after the pilot ended. Give it an owner, put it in the access review, and give pilots an end date. Its passwords and keys need looking after too — attackers once stole the keys of a single AI chat tool and used them to reach more than 700 companies’ customer data.

07

A sensible first step

A pilot plan that removes most of the risk:

  • A development copy, a read-only server and a named, limited login — never admin.
  • One use case, a small group of people, an owner and an end date.
  • Its answers checked against numbers you already know.

Widen it a step at a time as it earns trust.

08

Six questions to ask of any MCP server

Whether it’s IBM’s, an open-source one or built in-house. You don’t need to be technical to ask them; whoever looks after TM1 should be able to answer.

  1. AccessWhose access does it use — the person asking, or an admin?With an admin’s, everyone who asks the AI gets the admin’s view.
  2. ChangeCan it only read, or can it change things?Start read-only. Changes only where models are built — never on production.
  3. ReachWhat can it reach, and what’s kept out?Payroll, security and anything price-sensitive shouldn’t be reachable at all.
  4. CheckingWho checks its work?Its changes are reviewed, and its numbers checked before they go anywhere important.
  5. RecordIs there a record of what it looked at and changed?“Who looked at the salary cube last quarter?” should have an answer — AI included.
  6. OwnerWho owns it?A named person, in the access review, with an end date for pilots — and known answers to who built it and where its passwords live.
09

The short version

MCP lets AI work directly with your planning model. It’s worth exploring, and more doable than it sounds — as long as it’s set up on purpose.

Treat every MCP server like a new starter: limited access, someone checking its work, and nothing it does unrecorded.
