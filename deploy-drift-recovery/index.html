When PROD drifts:
baselines, reseed and recovery

Drift means the target server no longer matches the version it was last given. This article explains what that means, what reseed does and does not do, and the two ways to fix it.

Tested on TM1 v11 · DEV + PROD pair Related Shipping a TM1 change Status Published November 2026

01

What drift means

A deploy puts a version of the model on the target server. That version is the last received version. Drift means the target no longer matches it.

WordWhat it means here
TargetThe server receiving changes, usually PROD.
Last received versionWhat the last deploy put on the target.
DriftThe target no longer matches that version.
BaselineA local snapshot used for comparisons.
ReseedReplace that local snapshot with the target’s current state.
ReleaseThe files built from one closed change set for one target.
Catch-upAn admin-only release that ships every difference between DEV and the target.

Work in progress on DEV is normal. Drift is specifically the target disagreeing with what it was last given.

02

Why it happens

The usual cause is a direct edit on the target: someone changes a view, rule or cell in Architect or PAW, outside the deploy path.

A read-only target blocks normal writes from the IDE. It is a useful guard, but it is not a TM1 lock. A TM1 admin can still edit through other tools. So drift is possible, just rare.

A direct edit is not always a mistake. Sometimes it is a real fix made in a hurry. The question is not who broke it. The question is whether the change should be kept.

03

Two different references

The tooling has two reference points, and they are easy to confuse.

The baseline is a local snapshot used for comparison and recovery. The last received version is the state the last deploy created. They can match, but changing one does not change the other.

04

What reseed does

Reseed writes a new local baseline from the target as it is now. It does not change the target. It does not change the last received version. It does not clear drift.

ActionChanges the target?Changes the last received version?Clears drift?
ReseedNoNoNo
Restore the targetYesNoYes
Port the change to DEV and release itDEV, then the targetYes, after deployOnly after the target is restored

Reseed is for a server with no baseline, or one you deliberately want as a new starting point. It is not a deploy, and it is not a drift fix.

Do not trust the reseed message on its own. A baseline can be reseeded while the target still differs from what it was given. Check the drift report again.

05

Two ways to fix drift

Once the drift report shows what changed, decide whether to keep the direct edit.

Remove it: restore the target to its last received version. Check drift again. It should be empty.

Keep it: make the same change on DEV in a change set, then release it. But restore the target first, or Review will still stop. The release then applies the change with review and approval.

There is no automatic revert or promote. Both were tried and removed because they created new ways to lose work.

06

Catch-up can leave drift

A catch-up ships every difference between DEV and the target. It is an exception, not a normal deploy. After it runs, some drift can remain:

  • target-only objects you did not tick for deletion;
  • view or hierarchy changes written back by TM1;
  • subsets applied over REST that do not exactly match the release.

The same rule applies afterwards: the target must match what it last received before the next normal deploy.

07

The recovery checklist

  1. Read the drift report. Name every changed, new or deleted object.
  2. Decide: keep or remove. Do not reseed first.
  3. If removing, restore the target. Put it back to the last received version.
  4. If keeping, make the change on DEV. Put it in a change set and release it.
  5. Restore before Review. The release cannot pass while the target still differs.
  6. Check drift again. The drift report is the proof, not the reseed message.
  7. Record the outcome. The release and approval appear in Deploy History.
