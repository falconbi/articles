Shipping a TM1 change:
change sets, releases and drift

Every change should reach production with its own record, tests and approval, without carrying anyone else’s unfinished work. This is how that works, including what happens when someone edits PROD by hand.

01

One change, one record, one release

A deploy has to answer four questions before anyone can trust it:

A change set records the changes one person made on one server. For each save, it stores the object, what changed, the before and after, and who made the change. It is not a copy of the model, and it is not a Git branch.

A release is the set of model files built for one target server. It starts from what that target last received and adds only the changes in one closed change set. It is the thing you approve, and the thing the target receives.

WordWhat it means here
Change setThe list of saves one person made on one server.
ReleaseThe files built from one closed change set for one target.
CommitA saved state of DEV in Git history.
DeployApplying a release to its target server.
TargetThe server receiving the release, such as PROD.

The rule. A release contains only the changes in its change set. Nothing else goes with it.

02

Any two servers, one history

A deploy has a source server and a target server. Most teams call the source DEV and the target PROD, but the pattern works with any two servers. Some teams add a TEST or QA server in between.

  • DEV — where the model is built and changed.
  • TEST / QA (optional) — a copy of PROD used to try the release on realistic data before it reaches users.
  • PROD — the live model people use.

A common path is DEV → TEST → PROD. You can also deploy straight from DEV to PROD. The same rules apply either way.

A Git repository sits between them. It holds the model’s history and gives each target an exact release to receive.

A target does not receive “whatever is on DEV today”. It receives a set of files built for it, containing only the objects in the change set plus anything a dependency genuinely requires.

Deploying to TEST, then PROD

TEST and PROD are separate targets. A pass on TEST does not move anything to PROD by itself. The same change set is the source for both, but each target gets its own release and its own approval.

  1. Ship to TEST. Choose TEST as the target, build the release, review, approve, deploy and verify.
  2. Run the checks on TEST. Confirm the model and the numbers behave on realistic data.
  3. Ship to PROD. Open the same change set, choose PROD, build a new release, review, approve, deploy and verify.
  4. Approve again for PROD. The TEST approval does not cover the PROD release.

If you tested several change sets, ship them to PROD in the same order, one at a time.

Do not use catch-up as the promotion step. A catch-up ships everything that differs between DEV and the target — not just what passed on TEST. It is admin-only and can carry work that was never tested.

TEST and PROD give the same release only if they start from the same state. If TEST is not aligned with PROD, or has extra changes, the PROD build can add different files. Review the PROD build again; do not assume it matches TEST.

One current limitation: a change set shows only the last server it was shipped to. After TEST it may look finished. Use Show deployed, open the set, then choose PROD and build a new release. The tool allows this, but the screen does not make it obvious yet.

03

The change set is personal

Each person has at most one open change set per server. Your saves go into yours. A colleague’s saves go into theirs. The list is shared, so everyone can see who owns what — but the records are separate.

A release includes only the objects in your change set. Other changes stay on DEV and are listed under Left on DEV. If you try to add an object owned by another change set, or a dependency needs one, the release stops and names that set. It will not pull in their unfinished work. It works at object level, not line level: if two people edit the same rule or process, coordinate before releasing. Every save must belong to an open change set. If none is open, the IDE asks you to name one.

If two people edit the same TI process

There is no automatic merge inside one object. DEV holds the last saved text of the process, not two versions side by side. If both people save, the later save replaces the earlier one, and a release would ship whatever is in DEV at that moment.

You cannot remove one object from a change set. The entries are a record of what happened. So the choice is which set ships the agreed process — or whether to make a fresh set for it.

  1. Stop before building or deploying anything. Agree who owns the process for this change.
  2. Compare both intentions. Open the change report and the process history. Git keeps both saves even though DEV only shows the last one.
  3. Write one agreed version. One person saves the combined, final process on DEV.
  4. Ship one set. Only one set should carry the process to PROD, after the final text is agreed.
  5. Then ship the other set’s other work. Leave the process out of it. In the Build panel, the process should now show no file change against the new target state. If it still shows as changing, stop and reconcile again.
  6. If ownership must be clean, make a new change set containing just the agreed process and ship that first. Then the older sets no longer carry a process change.
  7. Check the target. After deploy, confirm the process on PROD matches the agreed version.
If the second set…Do this
contains only the processLeave it closed and undeployed. Do not ship it.
contains other work tooShip the agreed process first. Then ship the other work; the process should no longer show as changing in Build.
must have clean ownershipMake a new set containing just the agreed process and ship that first. The older sets then ship only their other work.

The safer habit is simpler: one person owns a process at a time. Use the change-set note to say who owns it and what it is for.

Before you start the deploy, open the change report. This is the first check. It groups entries by cube, dimension and process and lets you open a before/after diff for each object. Use the note field to say what the work is and why it exists. Both are useful when someone reviews the release a week later.

04

One release at a time — except catch-up

The normal rule is one closed change set per release, in order. That keeps the release small enough to review and attribute.

A catch-up takes everything that differs between the version the target last received and DEV’s current saved version — across multiple change sets — and builds one release. It is for abnormal cases: a target far behind, a model that reached PROD before change-set releases existed, or a long gap.

It is not the everyday path. It is admin-only, it does not let you select individual sets, it does not cover open sets, and it can leave drift behind. Treat it as a deliberate repair, not a faster deploy.

05

What goes into a release

A release is a saved set of model files. The IDE starts with the version the target already has, then adds only the files changed by your change set. Everything else on DEV stays out.

What the target already has + your change set = the release. Nothing else from DEV is included.

The release panel shows two lists. Included means it will ship. Left on DEV means it will not.

To add something from Left on DEV, look for a tick box next to it. Tick it, then click Build release again. Only items with a tick box can be added. If a row names another change set, you cannot add it — ship that set first.

If an included object needs another file, the IDE adds it automatically and lists it under Added because something in the release needs it. If that file belongs to another change set, the build stops and names the set.

What this means:

  • A release may include a few files you did not edit. This happens when one object needs another.
  • The panel lists them before approval, so the approver sees them too.
  • If an extra file belongs to someone else’s change set, you cannot add it. Their set must go to the target first. Then build your release again. If their set is not ready, your release has to wait.
  • If you did not expect the dependency, stop and check why your object needs that file.
06

The wizard: before, steps 1–8, after

The table below is the order. The top row is before the wizard, the middle eight are the wizard steps, and the bottom row is after it.

WhereWhat happens
Before the wizardReview the change report and write the note. This is the first check.
Step 1 — TestRun the model’s stored tests. A blocking failure stops you here.
Step 2 — CloseClose the change set. It records the tests and the exact entries.
Step 3 — CommitSave DEV to Git. This is history, not the release.
Step 4 — Build releaseBuild the files for the target. Check the three lists below.
Step 5 — ReviewCheck the list of changes the target will receive. Drift check — see section 07.
Step 6 — ApproveApprove this exact build, with a note.
Step 7 — DeployApply the build to the target.
Step 8 — VerifyCheck the target again. Drift check — see section 07.
After the wizardHandle any drift (section 07); check Deploy History.

At step 4, check these three lists

  • Included — will ship.
  • Added as dependency — also ships, because an included object needs it.
  • Left on DEV — will not ship. This is other work or work outside your set.

If something is in the wrong list, stop. Fix the change set or rebuild before you approve. Approval is for this exact build. If you rebuild, approve again.

07

Drift

This is the one place in this article that explains drift. The wizard only checks it at Review and Verify.

Does the target still match the version it was last given? If someone edited PROD directly, it does not, and the deploy pauses.

The wizard checks twice on purpose:

  • At Review, before deploy: “Is it safe to apply?” If the target changed, stop.
  • At Verify, after deploy: “Did it land exactly?” Compare the target with the new build.

The tool also checks once more at the moment it applies, because the target could change between Review and Deploy. The first check protects the target; the last check proves the deploy landed.

This should be rare. A read-only PROD posture blocks normal IDE writes, but it is not a TM1 lock: an admin can still edit in Architect or PAW. When drift happens, it has to be handled deliberately.

If the edit was a mistake, restore the target to the version it was last given. If the edit was intended, make the same change on DEV and release it. But restore the target first, or Review will still stop.

Reseed is not a drift fix. Reseed replaces a local comparison copy. It does not change the model and does not clear drift. The full recovery guide is When PROD drifts.

08

History and audit

Every successful release leaves a record: who shipped what, when, to which target, the approved build, and the result. Deploy History also keeps copies of the target before and after. The approval is tied to the exact build, so rebuilding it means approving again.

This is the point of the whole structure. Not that the deploy is clever, but that after it happens someone can reconstruct exactly what changed, who approved it, and whether the target received it.

09

The short version

  1. Work in a change set. One open set per person, per server.
  2. Review the report and write the note. It is the release’s explanation.
  3. Close only when the tests are green. Block failures stop the journey.
  4. Build on what PROD last received. The release carries one set, not DEV.
  5. Check drift before approval. A direct edit pauses everything.
  6. Approve the exact build. A rebuild needs a new approval.
  7. Verify after deploy. History is the audit trail, not a memory aid.
