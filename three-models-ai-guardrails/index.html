Three Models,
One Lesson

Three TM1 models built by an AI through an MCP: an allocations model, workforce planning, and a statutory consolidation. The first went wrong in instructive ways. The third matched 26 published worked answers. The AI did not get smarter in between. The system around it did.

01

Why write this

Most AI stories show the result. This one shows the progression — three models, built one after the other, by the same AI and the same person. The first build made beginner mistakes. The third built a statutory consolidation engine that matched every published answer it was tested against.

The interesting part is what changed in between. It was not the AI. It was the rules, the checks and the way we worked together.

02

The setup

A TM1 v11 server, and a browser IDE for TM1 with the MCP built into it. The MCP is the set of tools the AI uses to build and inspect the model: dimensions, cubes, rules, processes, views, and stored checks. Because it lives inside the IDE, the AI and the person share the same tools and the same guardrails. Every change the AI makes goes into a change set, and the person reviews, tests and deploys it from the same screens.

03

Build 1 — allocations: the mistakes

The first end-to-end build was an operating-expense allocations model. It worked in the end. Getting there showed exactly where an AI goes wrong in TM1:

  • Wrong dimensionality. It baked the subsidiary into cost-centre names (“Benefits North”, “Benefits South”) instead of adding a dimension. That is a modelling mistake, not a TM1 quirk — and the hardest kind to undo later.
  • TM1 traps. A three-argument attribute function that returned blank. Attributes written on elements created in the same Prolog, so “element not found” at run time. A three-deep IF in a rule that quietly returned zero with every input correct.
  • Views that would not render in the IDE, until rebuilt as native views.
  • Checking by hand. About 175 tool calls, about half of them reading cells to verify numbers. The checking was as much work as the building.
04

Mistakes into rules

Every mistake was turned into something that stops it happening again. Each lesson went to one of three places:

Where the lesson wentExampleWhy there
A lint rule — checked before anything is writtenAttributes on new elements belong in the EpilogThe AI cannot bypass it
The tool's own description“Native views by default”Seen on every call
The build guide the AI reads first“Get the dimensionality right first”Judgement, not a check

Learn once. A mistake made twice is a process failure, not an AI failure. Write the rule down where the AI will meet it.

05

Build 2 — workforce planning: deployment

The second build was a workforce planning model: versions and assumptions, pay rates, a hiring plan, FX, and employee income tax through to gross-to-net pay. It went through several rounds — a design review and rebuild, then house conventions, then versions.

The real test was not the build. It was deploying it: through the IDE's pipeline, from a development server to a production server, then comparing the figures. They matched to the cent.

The first real deploy also exposed nine bugs in the deploy pipeline itself. All were fixed. That is the point of doing it for real.

06

Build 3 — consolidation: test first

The third build was a statutory group consolidation: ownership and control at any depth, goodwill and non-controlling interests, step acquisitions and disposals, foreign currency translation, and consolidation of sub-groups.

This time the expected answers came before the build. Published worked examples — with their answers — were turned into stored checks first. Then the AI built until the checks passed.

  • 26 published worked examples, all matched.
  • Over 150 stored checks, run after every change.
  • One published answer turned out to be wrong. It was corrected from first principles, and the model matched the correction.

Later additions — registers so each acquisition is entered once, and a way to set up groups — were built the same way: copy a proven test case, rebuild it the new way, and require the results to be identical, cell for cell. They were. The tests also found real bugs the reviews had missed.

From trusting to checking. In build 1, I checked the AI's work by hand. In build 3, the checks were written before the work. The AI stopped being trusted and started being checked.

07

Working together

This was a partnership, and both sides got better at it.

What I brought: experience from more than 60 projects, design standards, and a clean process definition. Most of my work was reviewing and explaining, with some deeper insights that shaped the design.

What the AI brought: speed, arithmetic, research, tireless checking, and written records of everything.

Corrections went both ways:

  • The AI once described a sign-in route as “lab-proven” when it had never been tested. When that came to light, it was corrected — publicly, in the documentation.
  • I suggested checking production for out-of-band changes through Git itself. The AI set up a lab test; it worked; it is now the design.
  • The AI reviewed its own code before running it and caught real bugs — once, a rename that would have silently turned a sub-group into a top-level group.
  • The tests caught what neither of us did — for example, a company that bought another company before it was itself acquired.

The rules made the partnership work. Clear house rules, approval before changes, and evidence for every claim. Without them, speed would have been a risk.

09

What I learned

  • The AI did not get smarter. The system did. Rules it cannot bypass, checks written before the work, changes in change sets, evidence for every claim.
  • Dimensionality is still the human's job. The AI builds fast; it does not yet design well without guidance.
  • Known answers turn “looks right” into “is right”. Find the test data before building.
  • Do it for real. A deploy to a real server found nine bugs a demo never would.
  • Write everything down, as you go. It made the next build better and made mistakes cheap to fix.
  • It still needs an expert. Every decision that mattered came from experience. The AI made that experience go much further.
10

Where it is going

The same lessons are now moving into the tools themselves:

  • Tests live in the model, not in the tool — they travel with it, and run on development and production.
  • Deployment through TM1's own Git integration, with the IDE adding what Git cannot do and a readiness check before every push.
  • An AI that builds inside the same gates as a person: change sets, checks, approval.

Three models in, the conclusion is simple. AI is genuinely useful for building TM1 models — when the guardrails come first.
