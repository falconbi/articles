Self-referencing COA to tiered reporting dimensions

A reusable pattern for converting a flat, self-referencing chart of accounts into standalone reporting-level dimensions — with a full validation net — in a planning tool without native ragged consolidation. Formulas are shown in Pigment syntax; the structure ports to any tool with dimensions, self-referencing properties, and item lookups.

Pigment Hierarchy · COA Validation pattern Reusable design

Published 19 August 2026

Part of the hierarchy patterns set

Ragged Hierarchies — Concepts & Pattern Selection explains the underlying problem and the choice between the Balanced and Lean patterns. This document applies the same ideas to a specific case: a chart of accounts with multiple financial-statement frames and dirty source data.

01 — The problem

The problem

Source systems export a chart of accounts as a single flat list with one self-referencing parent property — each row names its immediate parent, and the tree is implied. That shape is awkward to report from: you cannot pivot cleanly by "reporting level", roll up consistently, or validate the tree.

The goal is to convert that flat list into N standalone dimensions, one per reporting tier, so that any downstream model can slice by a stable, explicit level — while maintaining a manual safety net for the gaps and errors that arrive in every source export.

Two complications make this non-trivial.

Ragged depth. Different financial-statement frames have different heights. A leaf account in one frame sits at a different absolute depth than a leaf in another.

Dirty source data. Exports arrive with missing parents, wrong account types, and occasional cycles. The transform must be defensive and self-validating.

The trade

The pattern buys stable, explicit reporting levels and a validation net that localises every source error — at the cost of hand-written, hand-maintained scaffolding. A sound trade when the tree is deep, ragged, and dirty; overkill when it is not (see section 11), and largely redundant in a tool that consolidates ragged hierarchies natively (see the platform note in section 3).

02 — The frame model

The frame model

A frame is a root-to-leaf chain (here: Balance Sheet and P&L). Tier labels are leaf-relative: L0 is always the leaf, Lk is always k tiers above the leaf. What differs between frames is the absolute depth at which each tier sits.

The two frames below are worked examples, not fixed limits — the pattern takes any number of frames, each of any depth.

FrameChain (root → leaf)Max depthLeaf tierTop tier
BS (Balance Sheet)L4 → L3 → L2 → L1 → L05L0 @ depth 5L4 @ depth 1
PL (Profit & Loss)L3 → L2 → L1 → L03L0 @ depth 3L3 @ depth 0

The one equation that governs everything

A tier's absolute depth is fully determined by its frame:

depth(Lk, frame) = maxDepth(frame) − k
TierBS depth (max 5)PL depth (max 3)

L41— (PL has no L4)

The table above is the two-frame instance; the equation holds for any frame at any depth. Every depth-based branch later in this document is that equation unrolled. State it once; the rest is mechanical.

Two structural consequences worth internalising.

PL tops out at L3, BS at L4. The frames have different heights, so the top grouping tier differs. PL genuinely has no L4.

Shallow leaves exist. A posting account can sit directly at a grouper tier (e.g. a PL leaf at depth 2, where L1 normally lives) because a sub-tree is shorter than its frame's maximum. These are legitimate and need special handling in the mapping and validation logic — they are the single largest source of edge cases.

Tier count and frame count are parameters, not limits

BS-with-5-tiers and PL-with-4-tiers are this example's numbers. The pattern imposes no ceiling: a BS frame could be 6 tiers deep and a PL frame 5, or you could carry a third frame (Cash Flow, a KPI tree) with its own depth. The structure never changes, because everything is driven by maxDepth(frame) and the tier equation.

Manual extension required

Parent does not recurse. Every walk up the tree — the depth ladder, the short-name walk, the cycle and ceiling probes, and the leaf multi-hop lookups — is a fixed-length chain written out by hand. If a frame is deeper than the chains written, the extra levels are silently ignored. When you resize, lengthen every Parent chain to match the new deepest frame. The Depth Ceiling Warning (section 9) exists precisely because this step has no automatic safety.

To do thisChange this
Add a tier to a frameRaise that frame's maxDepth; the equation re-slots every tier automatically
Add a whole frameAdd a member to the Statement classifier; give it a maxDepth
Reach a deeper leafAdd one more Parent hop to the Depth ladder and the Short Name walk
Map a deeper tierAdd the Level N mapping property and its composite dimension

Everything scales by the same three moving parts. The depth ladder needs one IFDEFINED(Parent…) rung per possible depth, so its length equals the deepest frame's maxDepth. The tier flags have one flag Lk per tier, each firing at depth = maxDepth − k for every frame that reaches that tier. The composite tiers have one Level N mapping property, one standalone dimension, and one bulk-import hop per tier — linear in tier count.

The only numbers that change when you resize are the lengths of the chained Parent walks and the count of tiers. The logic — leaf test, maxDepth − k, "grouping node → 1 hop, leaf → k hops" — is invariant.

03 — Architecture

Architecture

Three components do all the work.

Flat — the imported source list. Holds all raw properties, all derived classification, all mapping, and all validation. This is where the work happens.

Level 0 … Level 4 — one standalone dimension per reporting tier. Populated from Flat by a one-time bulk import.

Validation + KPIs — data-quality checks on Flat, rolled into count metrics for monitoring boards.

Naming convention used throughout

PlaceholderMeaning
FlatThe flat source list
CodeUnique key (account code)
NameFull path property from the source export (colon-delimited)
ParentSelf-referencing dimension property — immediate parent only, plain input
StatementFrame classifier property (BS / PL)
L0 … L4Boolean tier flags on Flat
Level 0 … Level 4The standalone composite dimensions
Platform fit

This pattern is machinery to synthesise a ragged hierarchy in a tool that will not walk one natively. Every hand-written Parent.Parent… chain, every per-tier composite dimension, every bulk-import hop exists because the modelling layer cannot recurse a self-reference and roll up on its own.

Pigment, Anaplan — the pattern earns its keep. There is no native ragged consolidation, so a tiered-dimension build is the correct approach to stable, sliceable reporting levels.

TM1 / Planning Analytics — most of this machinery is unnecessary. A single dimension with native consolidations handles ragged depth directly; the depth ladder, the tier flags, and the composite split are solving a problem the engine already solves. Port the ideas — settle-then-derive, the leaf test, the validation checks — not the scaffolding.

04 — Source properties

Source properties

Raw imported

ParentDimension → selfImmediate parent only, no formula. When the export supplies no parent, it is typed in by hand. Because the property is never formula-driven, no separate "manual override" field is needed — the property is the override point.

Manual overrides and the settle-then-derive pattern

Raw exports get things wrong. Patching the derived chain is safer than fighting the import on every refresh. Every override follows one shape:

IFDEFINED(override, override, calculated)

Add override properties for anything the source gets wrong: Manual Account Type Override, Manual Statement Override, Manual Depth Override.

Account Type (Settled) — the effective type every downstream formula reads:

// Manual override wins; otherwise fall back to the raw imported type.
IFDEFINED(Flat.'Manual Account Type Override',
          Flat.'Manual Account Type Override',
          Flat.'Account Type')

Statement — looked up from the settled type, so a type correction cascades:

// Frame classification, derived from the settled type.
// A Manual Account Type Override flows through to the statement automatically.
'Account Type'.Statement [BY: Flat.'Account Type (Settled)']

Derive from settled values, never raw

One override then cascades correctly through every dependent property. If Statement derived from the raw type, correcting the type would not fix the statement — you would need to override both. Derive from settled values and the chain repairs itself.

05 — Depth

Depth

Depth is the count of hops from the root (root = 0). A manual override wins; otherwise walk the parent chain, testing the longest chain first and falling through.

// Depth = number of hops from root.
// Manual Depth Override wins when it is set.
// Ceiling: an account deeper than max depth would misreport — see Depth Ceiling Warning.
IFDEFINED(Flat.'Manual Depth Override',
  Flat.'Manual Depth Override',
  IFDEFINED(Flat.Parent.Parent.Parent.Parent.Parent, 5,
  IFDEFINED(Flat.Parent.Parent.Parent.Parent,        4,
  IFDEFINED(Flat.Parent.Parent.Parent,               3,
  IFDEFINED(Flat.Parent.Parent,                      2,
  IFDEFINED(Flat.Parent,                             1,
                                                     0 ))))))

Short name and display name

The source stores a full ancestor path in Name; the leaf label is the segment after the final " : ". Extract it once, then build a board-facing label.

Short Name — last segment of the colon-delimited path. The full nested FIND / MID ladder is mechanical — one branch per separator level up to the frame maximum. Generate it to match the deepest frame.

Display Name — the label shown on boards:

Flat.Code & "-" & Flat.'Short Name'
Common bug

Concatenate Code with Short Name, not with Name. On the flat list Name is the full path, so Code & "-" & Name renders the entire ancestor chain. On the composite dimensions Name is already short, so the two are equivalent there — but keep the flat-list formula pointed at Short Name.

06 — Tier flags

Leaf and tier classification

All flags are boolean and return BLANK, not FALSE, when the condition fails — preserving sparsity so they sum cleanly into counts.

L0 — the leaf test. The only criterion is "nobody names me as their parent":

// TRUE for leaves; BLANK for grouping nodes.
// Groups a count of 1-per-account by Parent: if this account's bucket is blank,
// nothing points to it as a parent, so it is a leaf.
IF(ISBLANK( (IF(ISDEFINED(Flat.Code), 1, BLANK)) [BY SUM: Flat.Parent] ), TRUE)

L1 … L4 — grouping tiers. A grouping flag is "not-a-leaf AND depth matches this tier's depth for the account's frame", applying the depth equation depth(Lk) = maxDepth − k:

// L1: non-leaf AND depth = maxDepth(frame) - 1   →  BS depth 4, PL depth 2
IF(ISBLANK(Flat.L0)
   AND ((Flat.Statement = Statement."BS" AND Flat.Depth = 4)
     OR (Flat.Statement = Statement."PL" AND Flat.Depth = 2)),
   TRUE)

L2, L3, L4 are identical with the depth values shifted by the equation:

FlagCondition (besides non-leaf)
L1BS depth 4 or PL depth 2
L2BS depth 3 or PL depth 1
L3BS depth 2 or PL depth 0 (the PL root)
L4BS depth 1 only (PL has no L4)
Priority

L0 takes priority over grouping flags: a shallow leaf sitting at a grouper depth is a leaf, never a grouping node.

07 — Composite mapping

Composite mapping

Each account gets one mapping property per tier (Level 0 … Level 4 on Flat), computing which item in that composite dimension it belongs to. All resolution reduces to one rule.

The resolution rule

Account typeResolution
Grouping node at tier L(k−1)1 hop up Parent → Level k
Normal leaf (depth = frame max)k hops up Parent → Level k
Shallow leaf (sits at a grouper tier)(depth − depth of Level k) hops, or BLANK if at or above tier k

A grouping node at tier L(k−1) is always one level below its tier-k parent — so exactly 1 hop, regardless of frame or depth. A normal leaf at depth maxDepth reaching tier k (depth maxDepth − k) needs maxDepth − (maxDepth − k) = k hops — so k hops, no branching on frame. A shallow leaf sits above the normal leaf depth; it maps with fewer hops, or resolves to BLANK where it legitimately sits at or above the target tier.

Only leaves need the depth/statement branching, because leaves can appear at multiple depths. Grouping nodes at a given tier are always one hop from their parent tier.

Generic template

// Level k mapping on Flat
IF(Flat.'L(k-1)',                                    // grouping node one tier below k?
    ITEM(Flat.Parent.Code, 'Level k'.Code),          //   → 1 hop, done
IF(Flat.L0,                                          // else, is it a leaf?
    <depth/statement-branched multi-hop lookup>,     //   → k hops for normal, fewer for shallow
    BLANK)                                            // grouping node NOT at tier k-1 → BLANK
)

Worked example — Level 2

// Grouping node at L1 → 1 hop. Leaves → depth-branched lookup. Everything else → BLANK.
IF(Flat.L1,
    ITEM(Flat.Parent.Code, 'Level 2'.Code),
IF(Flat.Statement = Statement."BS",
    IF(Flat.Depth = 5,                               // BS normal leaf: 2 hops
        ITEM(Flat.Parent.Parent.Code, 'Level 2'.Code),
    IF(Flat.Depth = 4 AND Flat.L0,                   // BS shallow leaf: 1 hop
        ITEM(Flat.Parent.Code, 'Level 2'.Code),
    IF(Flat.Depth = 3 AND Flat.L0,                   // BS leaf sitting AT the L2 tier: self
        ITEM(Flat.Code, 'Level 2'.Code),
        BLANK))),
    IF(Flat.Depth = 3,                               // PL normal leaf: 2 hops
        ITEM(Flat.Parent.Parent.Code, 'Level 2'.Code),
    IF(Flat.Depth = 2 AND Flat.L0,                   // PL shallow leaf: 1 hop
        ITEM(Flat.Parent.Code, 'Level 2'.Code),
        BLANK)))
)
Shallow leaf in PL

The PL shallow-leaf branch (L0 AND Depth = 2 AND Statement = PL → 1 hop → Level 2) handles an account with no L1 bucket: it has no Level 1 entry by design and maps straight to Level 2. This is correct behaviour, not a gap.

Level 3 and Level 4 follow the identical shape one tier higher — grouping node at L2 / L3 gives 1 hop; leaves branch by depth up to 4 hops; BS-only for Level 4. Generate them from the rule rather than hand-writing each.

08 — Composite dimensions

Composite dimensions

Each composite dimension carries Code, Name, Display Name, Statement, an immediate-parent input property, and chained-formula properties for every tier further up.

DimensionInput property (imported)Chained formulas (walk the chain)
Level 0Level 1Level 2, Level 3, Level 4
Level 1Level 2Level 3, Level 4
Level 2Level 3Level 4
Level 3Level 4—

Only the immediate parent link per tier is ever imported. Every hop above it is a live chained formula that re-resolves automatically if a lower import is later corrected. You never hand-populate the upper tiers — they walk the chain.

The one-time bulk-import mechanism

For each hop X → X+1 (e.g. Level 1 → Level 2):

  1. From Flat, pull rows where the child tier flag is TRUE (L1 = TRUE for the L1→L2 hop), together with Flat's already-computed Level 2 mapping value for each row.
  2. Bulk-write those (child item, parent code) pairs into the immediate-parent input property of the next composite dimension. In Pigment: update_list_property_input_data.
  3. This is one-way and one-time — not a live link. If Flat's underlying Parent mapping changes, re-run the import for the affected tiers. Nothing recalculates automatically upstream of the import.

Hops in a 5-tier build: L0→L1, L1→L2, L2→L3, L3→L4.

09 — Validation

Validation

All checks return 1 (problem) or BLANK (OK) so they sum into count-based KPIs.

Missing-mapping checks

Each fires only for accounts that should have a mapping at that tier, excluding those that legitimately sit at or above it.

Missing L0 — active leaf with no entry in Level 0:

IF(Flat.L0 AND IFDEFINED(Flat.Inactive, NOT Flat.Inactive, TRUE),
   IFDEFINED(ITEM(Flat.Code, 'Level 0'.Code), BLANK, 1))

The higher-tier checks follow the same shape, gated on the depths that require that tier:

CheckFires forExcludes
Missing L1BS depth-5 leaf, PL depth-3 leaf, PL L1 grouperPL shallow leaf (depth 2, L0) — legitimately has no L1
Missing L2BS depth-5 and depth-4 leaves, PL depth-3 and depth-2 leavesBS depth-3 leaf (it is the L2 tier)
Missing L3BS leaves at depth 5, 4, 3 (BS only)BS depth-2 leaf (sits at L3), all PL
Missing L4BS leaves at depth 5, 4, 3, 2 (BS only)All PL (no L4)

Integrity checks

Self-Reference Warning — a 1-hop loop (parent = self):

IF(Flat.Parent = ITEM(Flat.Code, Flat.Code), TRUE, BLANK)

Ancestor Cycle Warning — multi-hop loops (2–6 levels up loop back to self):

(Flat.Parent.Parent                                = ITEM(Flat.Code, Flat.Code))
OR (Flat.Parent.Parent.Parent                      = ITEM(Flat.Code, Flat.Code))
OR (Flat.Parent.Parent.Parent.Parent               = ITEM(Flat.Code, Flat.Code))
OR (Flat.Parent.Parent.Parent.Parent.Parent        = ITEM(Flat.Code, Flat.Code))
OR (Flat.Parent.Parent.Parent.Parent.Parent.Parent = ITEM(Flat.Code, Flat.Code))

Depth Ceiling Warning — chain continues past the frame maximum. Cannot be caught by testing Depth > N because Depth is capped by the same chain and will not report a value above the ceiling. Must be tested directly:

Do not use Depth > N for ceiling detection

The Depth property is capped at its ceiling value by the IFDEFINED chain. An item 8 levels deep still reports Depth = 5. Test overflow directly by checking whether a chain one hop beyond the ceiling resolves — not by comparing the capped depth value.

// Fires when a chain one hop beyond the ceiling resolves.
// Skipped when a Manual Depth Override is set (override takes responsibility).
IFDEFINED(Flat.'Manual Depth Override', BLANK,
  IFDEFINED(Flat.Parent.Parent.Parent.Parent.Parent.Parent, TRUE, BLANK))

Hierarchy Warning — combined flag:

Flat.'Self-Reference Warning' OR Flat.'Ancestor Cycle Warning' OR Flat.'Depth Ceiling Warning'

KPI metrics

// Count of accounts with no parent set.
COUNTBLANKOF(Flat.Parent)

// Count of accounts missing an account type.
COUNTBLANKOF(Flat.'Account Type')

// Count of hierarchy-integrity failures.
// COUNTALLOF returns BLANK for an empty subset, which breaks color-scale formatting.
// IFBLANK coerces it to a real 0.
IFBLANK(COUNTALLOF(Flat.'Hierarchy Warning'[FILTER: Flat.'Hierarchy Warning']), 0)
10 — Anti-pattern

Anti-pattern: text-derived parentage

An earlier approach parsed the colon-delimited Name path to infer parents by text-matching ancestor segments. Fragile string matching silently mismatched a segment, truncated Depth to 0 downstream, and corrupted the tree without any error.

The authoritative source of parentage is the Parent dimension property — manually maintained, never text-derived. Keep Name parsing for the display label only (Short Name), never for structure.

11 — When not to use

When not to use this pattern

The pattern is the right answer only when parentage has to be resolved inside the modelling tool. Before building any of it, check whether the problem can be moved upstream — because most of this machinery disappears if it can.

  • The source can export a level-per-column hierarchy. If the ERP or a reporting view can hand you L4 … L0 as explicit columns, import those directly. Nothing to derive.
  • Pre-processing before load is available. A SQL view or a dbt model can flatten the self-reference into tiered columns with a recursive CTE — one place, tested once, in a language built for graph walks. Land that in the tool and skip the in-model depth ladder entirely.
  • The hierarchy is shallow and fixed. Two or three stable levels that never go ragged do not justify the frame model, the shallow-leaf handling, or the per-tier validation. Map them by hand.

Reach for the full pattern when none of those hold: the tool must own the mapping, the source is flat and self-referencing, upstream pre-processing is not available, and the tree is deep, ragged, and dirty enough that the validation net earns its place.

12 — Reuse checklist

Reuse checklist

  1. Import the flat source with a self-referencing Parent dimension property left as a plain input (no formula), so source gaps can be hand-filled.
  2. Add Manual … Override properties for anything the source gets wrong, each wired IFDEFINED(override, override, calculated). Derive from settled values, never raw.
  3. Compute Depth by walking the parent chain, longest chain first.
  4. L0 = "nothing names me as parent". Lk (k ≥ 1) = "not a leaf AND Depth = maxDepth(frame) − k".
  5. One composite-mapping property per tier on Flat, using the single rule: grouping node at tier L(k−1) → 1 hop; normal leaf → k hops; shallow leaf → fewer hops or BLANK.
  6. One standalone dimension per tier: an immediate-parent input property (bulk-imported from Flat once per hop) plus chained-formula properties for every tier above.
  7. Add missing-mapping checks per tier (excluding accounts that legitimately sit at or above that tier), the self-reference / ancestor-cycle / depth-ceiling / combined integrity checks, and roll counts into KPIs with IFBLANK(COUNTALLOF(…), 0) so empty results render as 0 for conditional formatting.
