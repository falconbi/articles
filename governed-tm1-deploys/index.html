Governed TM1 deploys:
from change sets to TM1 Git

A deploy to production must ship exactly one change set’s objects — no more. This is how we got there: a home-built pipeline that fought us on every object type, TM1’s built-in Git that solved the format but quietly shipped the whole of DEV, and the release commit that finally made the rule hold.

01

The goal

We built a browser IDE for TM1 so that developers — and AI agents working for them — can build models fast. Speed is the easy part. The hard part is trusting what lands on production. Before anything reaches PROD, someone has to be able to answer four questions:

A change set is our unit of work: a named basket. While it is open, the IDE records every object you touch; tests run against it; then it is closed, approved and released. Approval, audit and accountability all hang on one rule:

Rule 1. A release ships exactly its change set’s objects — no more, and nothing else may slip in with it.

02

Where we started: change sets over REST

The first pipeline was ours end to end. It was scoped to the change set from day one, but every object had to be read and re-created by our own code over the TM1 REST API.

Every phase of a real workforce-planning model landed clean on DEV — then the deploy fought back:

PapercutWhat went wrong
Attribute valuesReplayed only when the deploy created the dimension, not on a redeploy
Subset collisionsSubsets were keyed by name only, so two Default subsets on different dimensions collapsed into one
Lossy viewsA named-subset axis read back as “all members”, so a phantom change entered the package
Unreadable viewsA view with an unresolved axis could corrupt the target instead of being refused
Manual post-deploy stepsSeed, build, load, create subsets and reprocess feeders — by hand, after every deploy
Baseline timingVerification ran before the manual seeding, failed, and left stale drift noise for next time

The model grew three “scar tissue” processes whose only job was to rebuild what the deploy failed to carry. We fixed all six — but the pattern was clear: we were maintaining our own copy of IBM’s object format, and every object type was a new place to be wrong.

03

Why we moved to TM1 Git

Since TM1 11.4 / Planning Analytics 2.0.7, TM1 can push its own model to a Git repository and pull it back. That means IBM owns the object format and the transport — rules and TI become plain text files, every push is a commit, and any git tool can read the history. We tested it on a DEV and PROD pair sharing one private repository.

It does a lot — but not everything. So we split the job:

CheckResultConsequence
Attribute values travelNoA value change produced an empty commit — the IDE writes values itself
Deletes propagateNoA pull never deletes — the IDE reconciles deletes
Drift detectedNoPROD pushes its live state to a prod-live branch; the IDE diffs it
Scoped to a change setPartlyA pull applies every change on the branch since the target’s last deploy

That last row is the one that mattered. The evaluation wrote it down plainly and marked it as a warning. We built the deploy anyway and treated it as a detail. It was not a detail.

04

The discovery: a pull ships the whole branch

Here is the thing many TM1 developers new to Git won’t expect. A pull doesn’t take objects — it takes a branch. Whatever is on the branch, PROD gets. Our first version pushed all of DEV to the dev branch, the approver approved that commit, and PROD pulled it.

With two developers sharing DEV, that breaks every goal at once:

  • Scope — A’s deploy ships B’s half-finished rules.
  • Approval — the approver approved A; the commit contained B.
  • Audit — the record says “A deployed change set 12”; PROD received more than change set 12.
  • Safety — nobody should have to check other people’s unfinished work before deploying their own.

The project owner asked the right question: “I assumed only the change set’s objects were deployed.” Every governance claim rested on that assumption. So the transport had to be bent to fit the rule — not the rule to fit the transport.

Lesson. An evaluation finding marked as a warning is a design decision waiting to be made. Ours was made by default — and found a week later by the person whose requirement it broke.

05

The fix: a release commit per change set

TM1 still pulls a whole branch. So we build a branch that differs from what PROD already has by exactly one change set. We call it a release.

How a release is built:

  1. Start from what PROD has. The base is the commit the IDE recorded at PROD’s last deploy — not TM1’s own “deployed commit”, which is overwritten whenever PROD pushes its live state for a drift check.
  2. Map the change set to files. A process is its .json and .ti; a cube its .json and .rules; an MDX view its .json and .mdx.
  3. Copy only those files from DEV onto the base. Deleted objects are removed. Nothing else moves.
  4. Commit to release-<target> — one release branch per target.
  5. Record it on the change set, so the approval is bound to that exact commit.

Two gaps needed their own answer:

  • Subsets and views. TM1 Git’s pull has no operation for them — they never land. So straight after the pull, the IDE applies each included subset and view from the release’s own files over REST: MDX subsets keep their expression, static subsets their elements, MDX views their query, native views their axes.
  • Deletes and attribute values. A reconcile step applies only what the change set recorded.

Proven in the lab. Rule, dimension element, process, chore, MDX subset, static subset, native view and MDX view — all eight arrived on PROD, and nothing else did.

06

The safety design

The deploy is a sequence of gates. It stops at the first one that doesn’t hold, and every refusal says in plain words what to do next.

Around the flow, three rules hold on the server itself:

  • PROD is read-only to editing. Saves from the IDE — and from the AI’s tools — are refused. The only way in is an approved release.
  • Only built releases deploy. First-time setup is the only whole-model path, and it refuses once a target has been deployed.
  • Change sets are owned. A change set belongs to one TM1 user on one server; nobody else’s work rides along.

The drift pause is deliberate. When PROD has been changed by hand, the IDE doesn’t revert it or copy it back automatically. A developer re-applies the change on DEV in a change set, and it is released like any other. Slower — but nothing is lost, and everything is approved.

07

Lab lessons: TM1 Git quirks

Every one of these was found by running real deploys against a DEV and PROD pair — not by reading documentation. Unit tests passed throughout; the lab is where the deploy actually broke.

QuirkSymptomFix
TM1 forbids / in branch namesPull refused for release/PRODBranches are named release-<target>
Short vs full commit IDsTM1 reports a short ID, git a full one — the approval check said “moved”Exact match, or a prefix of 7+ characters
DeployedCommit is overwrittenPROD’s drift push reset it, so the next release was built on the wrong baseThe IDE records the deployed commit itself
Pull plans expire in secondsA plan created early returned 404 on executeCreate, check and execute in one step
Plan operations are textUpdate Cubes('X'), Skip …Every non-Skip operation must be in the release, or the deploy refuses
Subsets and views never landThe plan has no operation for themApplied over REST after the pull, then verified
First pull is a full overwriteA never-pulled target gets every objectA separate first-time setup path, refused once deployed
A view title with a deleted memberSelected: null blocks the whole pullA readiness check refuses it before push

A check that cannot fail is worse than no check. Our post-deploy verification read PROD’s “previous” commit after the deploy had already recorded the new one. The comparison was empty, so it verified nothing — and always passed. Because it always passed, it was trusted.

08

How the work was done

Three AI agents and one person built this, each with one job — and no agent both wrote and approved its own code.

The publish step matters. The private working branch carries client model work, so its history is never pushed. Each batch is replayed onto a clean branch from the public copy, checked for private names and data, and only then published for review.

What the separation caught:

  • A failed subset apply still showed “Applied” and marked the change set deployed — found in review, fixed before merge.
  • The verify-nothing bug above — found by reading the code, not by a failing test.
  • The whole-branch problem — found by the person, not by any agent. Agents check what they are asked to check; the requirement has to be stated.
09

Lessons learned

  1. Write the rule down first. “A release ships exactly its change set’s objects” is now rule 1. Written on day one, it would have caught the whole-branch pull on day one.
  2. A partial finding is a decision. Resolve every warning in an evaluation before building on it.
  3. Bend the transport, not the rule. TM1 Git pulls branches, so we build branches that differ by exactly one change set.
  4. Trust your own record over the tool’s. TM1’s deployed commit moves under you; the IDE’s record doesn’t.
  5. Refuse loudly; never succeed silently. Every gap stops the deploy or marks it failed, with a plain message saying what to do.
  6. Keep humans in charge of drift. Every automated revert or promote we tried opened a new way to lose work.
  7. The lab decides. Unit tests passed while the deploy was still broken. Only a real DEV and PROD pair finds those.
  8. Separate the builder from the reviewer. The same agent should never write and approve a change.
10

What’s next

  • Automatic checks on every pull request: tests, build and lint.
  • Safe handling of object names containing an apostrophe, everywhere.
  • Retire the automated drift revert and promote paths.
  • Split the 4,000-line server file into smaller modules.

The deploy is open source and in preview: github.com/falconbi/tm1_ide. Tested in the lab, not yet production-proven — try it on test servers and tell us what you find.
