This guide is about TM1 itself — it applies whatever tool you use (PAW, TM1py, TM1 IDE, vendor tools or your own scripts). Facts from IBM, vendors or well-used open-source libraries are linked under Sources, and anything not yet confirmed on a real server says so.

The two-minute version.

  • Signing in proves who you are. What you may see and change is always decided inside TM1, by its own security groups — however you signed in.
  • How you prove it depends on how the server was set up: TM1’s own passwords, the company directory, Cognos, Windows, or (on v12) the company’s identity provider.
  • Once in, you get a key card (a session) so you aren’t asked again. Good tools reuse it.
  • On v11, three wrong passwords lock the account — watch out for tools and schedulers that keep retrying an old password.
  • Encrypt the connection (TLS), and never leave admin on a blank or sample password.

01

The big picture

Signing in always answers two questions:

  1. Who are you? — authentication. Proven with a password, a key, a ticket from Windows, or a pass from another system that already knows you.
  2. What may you do? — authorisation. In TM1 this is always decided inside TM1, by the security groups a user belongs to (}ClientGroups). However someone signs in, TM1’s own security still decides what they see.

Once TM1 is satisfied about who, it hands back a session ticket — a cookie called TM1SessionId. A well-behaved program sends that ticket with every later request instead of signing in again. Think of it like a hotel key card: you show your passport once at the desk, then use the card for the rest of your stay.

Everything in the rest of this article is about step 1 — the different ways of proving who you are — except where it says otherwise.

02

A typical environment

Before the details, it helps to see where everything sits. Here is a typical company running Planning Analytics, drawn without the technical parts:

Think of it as an office building:

  1. Reception. Most people come in through PAW, in a web browser (or through Planning Analytics for Excel, which also goes through PAW). Developers’ tools and scripts often skip reception and go straight to the rooms, using the TM1 REST API. → 5.9, 4
  2. Checking your ID. Someone has to confirm you are who you say. That might be TM1 itself (its own list of passwords), the company’s staff list (Active Directory), Cognos acting as a badge office, or — on newer v12 systems — the company’s identity provider, the same sign-in you use for email. Which one depends entirely on how the servers were set up. → 4, 5, 6
  3. The key card. Once your ID is checked you get a key card — a session — so you aren’t asked again at every door. → 1, 9
  4. Each room has its own guest list. DEV, TEST and PROD are separate TM1 servers. Each has its own users and security groups, and decides for itself what you may open. Getting through reception does not get you into every room. → 1, 8
  5. Deliveries and robots. Scheduled jobs, data loads and integrations have no person to type a password or approve a phone prompt. They need their own kind of badge, and they are the most common cause of locked accounts. → 7, 9

Two more pieces sit in the background: the admin server, a small TM1 service that works like the building’s directory board (which servers exist, and where), and TLS, which makes sure nobody can listen in on the corridors → 10.

Asking the server (no password needed)

A tool can ask a TM1 v11 server which method it uses without signing in: send any request with no credentials and read the WWW-Authenticate line of the “401 Unauthorized” answer. Because no username is sent, this does not count as a failed login.

Answer containsMeaningStatus

Note the server hands out a session cookie even on the refusal — it is not signed in until credentials are sent.

5.1TM1 native security

In one sentence: TM1 keeps its own list of users and passwords. Documented

When you’ll see it: labs, smaller sites, and any brand-new server before it is switched to something else.

  tool ── "Authorization: Basic <name:password>" ──▶ TM1   (checks its own }Clients list)
  tool ◀────────────── TM1SessionId ──────────────── TM1

The name and password are only encoded (base64), not encrypted — which is why TLS (section 10) matters.

Setting it up: the default. Users are }Clients elements; passwords are set by an admin (TI AssignClientPassword, or the REST API).

Common problems: wrong password three times → the account is locked (section 9).

5.2TM1 users, LDAP password check

In one sentence: users still live in TM1, but TM1 asks the company directory whether the password is right. Documented

When you’ll see it: sites that want company passwords without installing Cognos.

  tool ── Basic <name:password> ──▶ TM1 ── "is this password right?" ──▶ directory (LDAP)
  tool ◀──────── TM1SessionId ───── TM1 ◀──────────── "yes" ─────────── directory

To a tool it looks exactly like native security — same header. Never single sign-on: a password is always typed.

Setting it up (tm1s.cfg): PasswordSource=LDAP, LDAPHost, LDAPPort (636 for secure LDAP), LDAPSearchBase (where users live), LDAPSearchField (usually sAMAccountName = the Windows user ID), LDAPUseServerAccount. Users must already exist in TM1 — add them by hand or import them with IBM’s ETLDAP utility, which only adds users (it never updates or deletes).

Common problems: user exists in AD but not in TM1 → can’t sign in; wrong search base → every login fails.

5.3CAM — username and password

In one sentence: TM1 trusts Cognos to check who you are; you type your company (directory) password. Documented; the header format is proven in practice by TM1py.

When you’ll see it: very common at larger sites — Cognos Analytics connected to Active Directory, TM1 in mode 4 or 5.

  tool ── "Authorization: CAMNamespace <name:password:namespace>" ──▶ TM1
                                          TM1 ── asks Cognos ──▶ Cognos ── checks ──▶ Active Directory
  tool ◀──────────────────── TM1SessionId ─────────────────── TM1

The namespace tells Cognos which directory to check (a site can have several).

Exact format (as used by TM1py): the word CAMNamespace, a space, then user:password:namespace encoded in base64 — e.g. jsmith:secret:AD becomes CAMNamespace anNtaXRoOnNlY3JldDpBRA==.

Setting it up: IntegratedSecurityMode=4 or 5, plus ServerCAMURI (Cognos’s internal dispatcher, e.g. http://cognos:9300/p2pd/servlet/dispatch) and ClientCAMURI (Cognos’s address for users, e.g. http://cognos/ibmcognos/bi/v1/disp). The first administrator needs a special routine — see section 8.

Common problems: wrong or missing namespace → 401; Cognos down → nobody can sign in to TM1; a user’s TM1 groups only refresh when they sign in again.

5.4CAM — single sign-on

In one sentence: you’ve already signed in to Windows; Cognos recognises you and gives you a passport, which TM1 accepts — no password typed. Documented; flow proven in practice by TM1py’s “gateway” option.

When you’ll see it: the same sites as 5.3, where Cognos is set up for Windows sign-in (Kerberos).

  1. tool ── GET gateway?CAMNamespace=<namespace>, with Windows sign-in (Negotiate) ──▶ Cognos gateway
  2. tool ◀────── passport (cookie "cam_passport") ───── Cognos
  3. tool ── "Authorization: CAMPassport <passport>" ──▶ TM1 ── checks with Cognos
  4. tool ◀──────────────── TM1SessionId ────────────── TM1

When TM1 refuses a request it tells the tool where to get a passport: its “please sign in” answer includes the Cognos address. Documented

Setting it up: TM1 as for 5.3 (mode 4 or 5 with the CAM addresses); on the Cognos side, the namespace and gateway set up for Windows sign-in (Kerberos), and the user’s PC on the domain.

Common problems: works in the browser but not from a script → the script isn’t doing the Windows sign-in to the gateway; passport expired → get a new one.

5.5Windows integrated login

In one sentence: TM1 trusts your Windows sign-in directly, with no Cognos involved. Documented

When you’ll see it: Windows-centred sites without Cognos; IntegratedSecurityMode=2 (choice) or 3 (Windows only).

How it works: the tool and TM1 use Windows’ own sign-in exchange (Negotiate — Kerberos, or the older NTLM). Your PC gets a ticket from the domain controller and shows it to TM1; no password crosses the network.

Setting it up: users exist in TM1 as DOMAIN\user; the TM1 service may need a service principal name (SPN) registered in Active Directory for Kerberos. A program can only do this when it runs as the Windows user, on a domain-joined machine (TM1py, for example, uses the Windows-only SSPI library for it).

Common problems: works on one PC but not another → SPN or delegation; mode 3 locks out anything that can’t do Windows sign-in (scripts on Linux, many web tools).

5.6v11 OpenID Connect

In one sentence: a v11 server can be told to accept sign-in from a company identity provider (Entra ID, Okta …) using the OpenID Connect standard. Documented that it exists; how a tool hands the result to TM1 — Unconfirmed.

When you’ll see it: v11 sites standardising on a cloud identity provider; tools that offer “sign in with your company account” against a v11 server.

How it works (as Cubewise documents it for its Canvas product): the tool is registered in the identity provider (client ID, client secret, the provider’s “discovery” address). When a user needs data, the browser is sent to the provider’s sign-in page (single sign-on passes straight through), comes back with a one-time code, and the tool uses that code to sign in to TM1.

Setting it up: SupportOpenConnect=T in tm1s.cfg (default off), plus registering the tool in the identity provider. Not available in v12, where the platform handles identity instead (5.7, 5.8).

Common problems: the tool’s return address doesn’t match what is registered in the provider → sign-in fails after the provider page; the user exists in the provider but not in TM1 → signed in, but no access.

5.7v12 in IBM’s cloud — API keys

In one sentence: people sign in through the browser with their IBM/company account; programs use an API key that carries the same rights as the person who made it. Documented by IBM; usage proven in practice by TM1py.

When you’ll see it: Planning Analytics as a Service (IBM’s cloud), for scripts, schedulers and tools that run without a person.

  tool ── Basic "apikey" : <the key> ──▶ https://<region>.planninganalytics.saas.ibm.com/api/<tenant>/v0/...
  tool ◀──────────── session ──────────
  TM1 database API: .../api/<tenant>/v0/tm1/<database>/api/v1

Setting it up: in Planning Analytics: your name → Manage API key → Generate key. Copy it straight away — it can’t be shown again. Sessions time out after 60 minutes idle.

Common problems: the key works but data is missing → the key has exactly its creator’s rights; key lost → make a new one and revoke the old.

5.8v12 on-premises and Cloud Pak for Data — app credentials and tokens

In one sentence: the platform’s identity provider signs people in; programs use an application ID and secret (or a ready-made access token) to get a short-lived token. Proven in practice by TM1py; IBM details vary by deployment — partly Unconfirmed.

When you’ll see it: TM1 Database 12 run on-premises or on Cloud Pak for Data, with the company’s identity provider (Entra ID, Okta, Authentik …).

  1. tool ── app ID + secret ──▶ platform's sign-in service
  2. tool ◀──── access token ──
  3. tool ── "Authorization: Bearer <token>" ──▶ TM1 database (instance + database name in the address)

First administrator: comes from the platform — e.g. on Cloud Pak for Data, platform administrators become Workspace administrators and TM1 admins on first sign-in; other users are added to TM1 with TI AddClient. Documented

Setting it up: the tool is registered once as an application in the identity provider (an ID, a secret and its return address); nothing is needed per user. For people, single sign-on is meant to work through the identity provider: if you’re already signed in there, you aren’t asked again. Exactly how a third-party tool gets a token that carries your identity, rather than the app’s, varies by deployment — Unconfirmed.

Good to know: IBM’s “authorized applications” (OAuth) for Planning Analytics support only interactive sign-in (a person in a browser); the non-interactive “client credentials” flow is documented as not supported there. Documented for PAW on Cloud. Whether PAW and the v12 engine accept tokens issued to a different registered application is Unconfirmed.

Common problems: a scheduled job can’t sign in → it needs app credentials, since the interactive flow needs a person; the token expires → the tool must fetch a new one.

5.9Through Planning Analytics Workspace (PAW)

In one sentence: PAW signs you in once and passes your requests on to TM1 for you. Proven in practice — lab.

When you’ll see it: wherever people use Planning Analytics Workspace — and for tools that reach TM1 through PAW rather than directly.

How it works: you sign in to PAW (which checks your login against its configured TM1 login server, or Cognos, or an identity provider); PAW keeps your session in cookies and forwards TM1 requests at <PAW>/api/v0/tm1/<server>/api/v1/…. Programs using this route must send PAW’s anti-forgery value (cookie ba-sso-csrf) back in a header (ba-sso-authenticity).

Setting it up: in PAW’s administration, the authentication mode (TM1 login server, Cognos, or an identity provider) and the TM1 servers it can reach.

Common problems: you can sign in to PAW but see no data on a server → you’re not a user on that server; PAW’s login server down → nobody can sign in to PAW.

Directory, CAM and single sign-on — how they fit together

They are three different things:

07

Programs, not people: scheduled jobs and integrations

Everything above assumes a person at a keyboard. A large share of sign-ins aren’t: nightly data loads, schedulers, integrations, reporting tools, scripts. They have no one to type a password, pick up a phone prompt or click “approve”, so the sign-in that suits people often doesn’t suit them.

Where it runsSigns inNotes
Chores and TI processes inside TM1No sign-in — they run inside the serverThe simplest option when the work can live in TM1.
Script against v11, native or LDAP checkIts own TM1 user and password (5.1, 5.2)Use a dedicated account, not a person’s.
Script against v11 with CAMA service account in the namespace, by username and password (5.3)Single sign-on (5.4) only works if the script runs as that Windows user on the domain.
Script against v11, Windows only (mode 3)Must run as a Windows user (5.5)Scripts on Linux can’t sign in at all.
Script against v12 in IBM’s cloudAn API key (5.7)The key carries exactly its creator’s rights.
Script against v12 on-prem / Cloud PakApp ID + secret → token (5.8)The interactive browser sign-in can’t be used unattended.

Good practice, whatever the method (general security practice, not TM1-specific rules):

  • One account per job or tool, never a real person’s login — so a password change or a leaver doesn’t silently break the overnight load.
  • Only the rights it needs, through TM1’s security groups. A data-load account rarely needs ADMIN.
  • Keep the secret out of the code — in a protected configuration file, an environment variable or a secrets store, never in a script that gets copied, emailed or committed to source control.
  • Remember lock-outs apply to robots too. One job trying an out-of-date stored password locks the account for every job that shares it (section 9).
  • Change secrets on a schedule, and know every place each one is stored before you do.

The very first administrator on a new server

Native (mode 1)A new server has user admin with a blank password. Sign in that way once and set a password immediately (TI AssignClientPassword('admin', '…'), or REST PATCH Users('admin') with {"Password":"…"}).
CAM (mode 4/5)TM1 only lists a CAM user after they have tried to sign in once. So: set mode 4 with the CAM settings → restart → sign in once with your CAM account (you get no rights yet) → set mode 1 → restart → sign in as admin → add your CAM user to the ADMIN group → set mode 5 → restart → sign in with your CAM account, now as administrator. A warning about blank and sample passwords. A brand-new TM1 server with admin and a blank password — or an IBM sample server (24Retail, Planning Sample) still on its published admin / apple login — is open to anyone who can reach it on the network. Set a real password before the server is reachable by anyone else, and change or remove the sample servers on any shared machine.

09

Sessions and lock-outs

Lock-outs. TM1 v11 allows 3 failed sign-ins by default (MaximumLoginAttempts in tm1s.cfg). After that the account is refused until an administrator resets its password or the server restarts. Documented — not applicable to v12.

Watch out for tools that keep retrying. Any program that keeps trying a stored password that has since changed — a scheduler, a dashboard that refreshes, an IDE polling in the background — will lock the account within seconds. A well-behaved tool tries once, reports the failure, and waits for a person.

Leaked sessions. Every successful sign-in creates a session. A program that sends the password with every request, instead of reusing the TM1SessionId ticket, creates a new session each time; they pile up until TM1’s session timeout. A real example: a lab server was found with 538 open sessions, left by an early version of the author’s own tool (the TM1 IDE) doing exactly this — careful code still gets it wrong. They show up in the Sessions list, in TM1 Top and in }StatsByClient, and they waste memory. A well-behaved tool signs in once per server, reuses the ticket, and closes the session (REST: POST ActiveSession/tm1.Close) when it’s done. Proven on a real v11.8 server

Measured, before and after fixing a tool to reuse its ticket (same server, v11.8): before — a new session on every request, 538 left open; after — a user browsing cubes, views and dimensions for several minutes added no sessions beyond the one created at sign-in. To check your own server, compare the Sessions list before and after using a tool — and remember that every separate program you run (including a quick check script) signs in once itself.

12

Checklists

If you run TM1 servers

  • Give admin a real password before the server is reachable by anyone else, and change or remove sample servers on shared machines (8).
  • Know which method each server uses, and write it down — including how you would get back in if Cognos or the identity provider were down (4, 8).
  • Encrypt connections with TLS, using certificates your tools can check (10).
  • Give programs their own accounts with only the rights they need (7).
  • Review who is in ADMIN and other powerful groups on every server, not just PROD.
  • Watch the session list now and then; a steady climb means a tool is leaking sessions (9).

If you write a tool or script that signs in

  • Ask before you sign in. A request with no credentials tells you which method the server expects, and doesn’t count as a failed login (4).
  • Try once. If a password is refused, stop and tell a person. Never retry a rejected password automatically (9).
  • Sign in once per server, reuse the session, and close it when you’re done (9).
  • One login per server. Never try one server’s password on another — each failure counts towards that server’s lock-out.
  • Check certificates by default, and make switching the check off a deliberate, visible choice (10).
  • Never store passwords in code or anywhere that gets copied or committed; never send them to a browser.
  • Let TM1 decide access. Run as the person (or a dedicated account), not as a shared administrator, so TM1’s own security still applies.
