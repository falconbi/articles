Pigment and TM1: matching the engine to the work

Both engines are fast enough for almost every planning team. The differences that matter concern the shape of the work: how it is divided across machines, and what happens when a calculation depends on its own result. In broad terms, each engine is inexpensive to change in the areas where the other is expensive. The summary below states the whole comparison; the sections after it explain why it takes this shape.

TM1 / Planning Analytics Pigment ~9 min read
01 — How each engine scales

How each engine scales

Pigment knows the size and shape of a calculation before it runs, so it can divide the work across several machines and add more machines as models grow.

TM1 holds the whole model in one machine's memory and computes each figure on demand. This makes live editing feel immediate, but it ties the model to a single machine, so it grows by using a larger machine rather than more of them. The property that makes TM1 quick to edit is the same one that fixes it to one machine; the property that lets Pigment use many machines is the same one that can make a heavy report pause when first opened.

02 — Calculations that feed themselves

Calculations that feed themselves

Some calculations depend on their own result. A running balance is the mild case: this period's closing figure is last period's closing plus the movement, so the calculation refers back to itself. The harder case is cross-charging between departments — one department bills another and is billed in return — where each department's cost depends on the other's.

No planning tool allows a calculation to depend on itself directly. Pigment handles this by laying the repetitions out in order — period by period, or pass by pass — so each step reads the previous one and nothing refers back to itself.

03 — When passes are not enough

When passes are not enough

Pigment's sequence of passes has a fixed length. For a running balance this is sufficient. For cross-charging that only settles after many rounds, a fixed number of passes may stop before the figures settle.

TM1 can continue until the figures settle, however many rounds it takes, but only on one machine. For cross-charging at scale, the reliable approach is to solve the calculation in the data warehouse, which can resolve it in a single step, and return the result to the planning tool.

Caveat

Solving the calculation outside the planning tool only helps if that outside layer is a governed data platform — one that tracks history, versions and where each figure came from. A set of loose files behind a connector provides none of that, and the case for moving the work there is weaker.

04 — How data is brought in

How data is brought in

TM1 includes a tool that both loads and cleans data and runs planning steps such as allocations and version copies. Pigment has no equivalent, by design.

Loading and cleaning move upstream, to the data warehouse or source system. The planning steps stay inside Pigment, written as formulas the finance team can read and change. So the absence of that tool means two things at once: the data preparation moves out, and the planning stays in.

Cases that depend on a second question

Some situations do not resolve until one further question is answered. Each looks like a single choice but turns on the detail underneath.

Large-scale apportionment

Does the cost flow one way, or in a circle?

One-way apportionment — spreading a single pool across thousands of cost-centre-by-product lines — favours Pigment, because each line is independent and the work divides across machines. Apportionment in a circle, where departments cross-charge until the figures settle, is different: solve it in the warehouse and return the result. If it must stay inside one tool, TM1 can run a circular calculation until it settles. The same term covers two different problems.

Many interconnected applications

Interconnected by sharing, or by calculation?

If the applications share the same structure and data — one master list feeding many business units — that favours Pigment, where a shared object is defined once and used live by every application. If instead the applications calculate through each other, with most figures depending on most others, holding it all in TM1's single shared memory is simpler than connecting many applications. Sharing points to Pigment; a single interwoven calculation points to TM1.

Models in constant change

Is the structure changing, or the logic?

If the structure changes — hierarchies reorganised, levels added or removed, trees of uneven depth — TM1 absorbs it with the least rework. If the logic changes — new drivers, new calculations — Pigment is quicker to change and to see the result. Structural change favours TM1; logic change favours Pigment.

Scope of this comparison

Every point above concerns the calculation engine only. For most buyers the decision is settled by adoption and day-to-day usability, which is a separate comparison from this one.

Choosing

Choosing

The decision is rarely about speed; both engines are fast enough for almost every team. It concerns the shape of the work. TM1 makes structural change and self-referential calculation inexpensive, and pays for it in scale and cross-application sharing. Pigment makes scale, sharing and logic change inexpensive, and pays for it in reshaping hierarchies and resolving circular calculations. Choose the tool whose inexpensive changes match the changes made most often.
